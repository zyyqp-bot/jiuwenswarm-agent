# 证据优先的多 Agent 工作台 — 设计

日期：2026-10-24 · 状态：待批准 · 目标截止：2026-11-10（大赛作品提交）

## 1. 意图与为什么是现在

本项目已有一个经过验证的多 Agent 底座：固定三成员名册、计划校验、执行账本、依赖/完成门禁、预算、事件去重、FTS5 检索、RRF、上下文预算、引用校验、汇总与返工。P0 全部退出条件由断言覆盖，P1 完成了工具面验证与一次真实回合。

但这些能力目前只以验证脚本存在，没有一个用户可以使用的形态。第二届全国人工智能应用创新大赛重庆区域赛的通用赛道要求“AI Agent 赋能千行百业”的真实业务作品，截止 2026-11-10 24:00，且必须先过校赛。因此目标不是继续补全框架，而是把已有能力收敛成一个**可演示、可复现、可审阅**的产品：

> 一个通用的 Agent 工作台：用户建立工作区、导入垂直领域资料、给出目标，Agent 自己规划任务并连续执行，交付一份每条结论都能回查到原文的成果。

通用性与垂直性的关系是产品叙事的核心：引擎不含行业逻辑，垂直领域由“语料 + 角色提示词 + Skill 配置”决定，换配置即换行业。比赛演示只用一个垂直，但架构必须证明它不是写死的。

**评审形式（用户 2026-10-24 确认）**：大赛不限平台与大模型，但要求提供一个**可登录的在线链接**供专家自行试用。因此部署、登录、并发隔离与公网安全是本期硬要求，不是收尾工作；“视频 + 仓库”不足。模型调用在服务端完成，密钥不下发浏览器。

## 2. 目标 / 非目标 / 反目标

### 目标

1. **自主规划与连续执行**：Leader 产出任务 DAG，Research/Engineering 按角色执行，门禁保证只有有效产物才放行，失败按要求有限返工。
2. **可审计**：结论级引用（不是答案级）、冲突保留、未知项显式、检索降级可见（`keyword_only`）。
3. **通用引擎**：语料、角色提示词、报告模板可替换；演示垂直不进入引擎代码。
4. **可演示**：Web 工作台能展示任务图状态、证据抽屉、带引用报告、预算与审计轨迹。
5. **可复现**：从空目录按 PROJECT.md §13 重建环境，跑通 demo 与评测。
6. **可在线评审**：公网 HTTPS 链接 + 登录；评委可自行建 run、看任务图与证据；会话隔离、并发与原预算受限；模型密钥只在服务端。

### 非目标（本期不做）

- 完整用户体系、多租户、计费、权限后台。登录只做**最小可用**：预发账号或访问码 + 签名会话，够评审使用与隔离会话即可。
- 评委侧的公网文件上传：公开链接只开放预置工作区；导入仅在本机/管理员模式可用，避免把解析器和写盘暴露给公网。
- 移动端、桌面端。
- 通用闲聊机器人（对话框不是产品主体）。
- GraphRAG、多模态检索、微调模型。
- 动态成员扩缩容（R10 仍是后续目标）。
- 集成 JoyCode 平台（大赛提供该平台，但不作为运行依赖；提交材料中说明关系即可）。

### 反目标（即使“能跑”也算失败）

- 演示中编造引用，或把未验证结论标成事实。
- 发现资料冲突却取平均/隐藏冲突。
- UI 很完整，但 Agent 实际上没有派任务，只是 Leader 单打独斗。
- 用模拟结果冒充端到端通过。
- 为了演示效果开启动态 spawn，破坏固定名册。
- 公网链接上暴露 harness 自带的 shell/文件工具——那等于把服务器执行权交给任何能说服模型的输入。真实回合已观察到 Leader 面前有 29 个工具，其中包含 harness 能力；上线前必须把它收敛到“团队协作 + 检索 + 提交结果”。
- 评委之间能读到彼此的 run、证据或产物；或用一条 run 耗尽全局模型预算。

## 3. 约束与已确认事实

| 约束 | 影响 |
|---|---|
| 上游源码锁定（agent-core `6df9699`、jiuwenswarm `3fea8d1`），不修改 upstream | 适配层承担所有差异 |

| 评审通过登录链接访问 | 需要公网 HTTPS、会话隔离、并发与成本上限；部署必须提前到 D5，不能留到最后 |
| 服务器/域名/备案资源未定 | 国内主机绑定域名通常需要备案，耗时不可控。需尽早确认可用资源；备选是境外小主机或临时隧道（隧道只用于联调，不作为评审链接） |
| 公网安全 | 关闭 harness shell/文件工具；模型密钥只在服务端；评委侧禁上传；全局限流与预算 |

用户已确认的决定：

- 产品是通用型，不是教育专用；某一垂直领域用 RAG 知识检索落地。
- 交付到“可演示 Demo + 完整提交材料”。
- 团队：单人，尚无指导教师（需尽快补，指导教师 0–2 名、计入总人数）。
- 演示语料：公开的行业政策/法规文件。

## 4. 产品形态

### 4.1 核心对象

- **Workspace**：一个垂直实例（语料集合 + 角色提示词 + Skill 集合 + 报告模板）。
- **Corpus**：导入的公开文件，带来源、版本、hash、授权 scope。
- **Goal**：用户写下的目标（不是聊天消息），可附约束与验收标准。
- **Run**：一次执行。包含计划、任务图、每个任务的证据与结果、预算、事件、最终成果。
- **Report**：结构化成果，每条 claim 带 kind 与 evidence_ids；冲突、未知、被裁剪证据单列。

**访问路径**：评委打开链接 → 登录（预发账号或访问码，签名会话）→ 选择一个预置工作区 → 输入目标或选一个示例目标 → 观看 run 实时推进 → 打开报告与证据 → 可导出 Markdown。本机/管理员模式额外开放语料导入、工作区创建与数据重置；公网链接不提供这些。

### 4.2 界面（MVP）

一屏工作台，四块区域：

1. **左：工作区、语料与运行控制**——工作区选择；文件导入（上传 → 解析 → 索引，展示成功/`keyword_only`/失败）；目标输入、约束、开始/停止、运行状态、预算与用量。演示语料预先导入，但导入流程本身可用，避免“只敢演示预置数据”。
2. **中：任务图**——DAG 节点实时状态（pending/blocked/in_progress/in_review/completed/cancelled），点击节点看指令、依赖、验收条件。
3. **右：证据抽屉**——选中任务/claim 时展示证据：原文片段、来源、版本、定位（页/节/字符区间）、检索方法与分数。
4. **下：成果与审计**——带 `[fact]`/`[inference]`/`[assumption]`/`[unverified]` 标记的报告；冲突与未知面板；事件时间线；导出 Markdown。

交互原则：运行中只读观察；失败任务的**定向返工发生在 run 内**（最多一次，开新 execution）。**MVP 不做跨 run 重跑**：run 结束后原生 team 已不存在，跨 run 重跑等于恢复 checkpoint 或新建 team 并对账，是另一个功能，明确不做而不是做一半。MVP 也不做计划编辑。

### 4.3 演示垂直（builder call，可替换）

默认选 **AI 治理与数据合规**：语料为公开的中国 AI/数据领域政策法规（如生成式人工智能服务管理暂行办法、数据安全法、个人信息保护法、算法推荐管理规定等），目标示例：

> “我们要上线一个面向公众的生成式 AI 客服，列出上线前必须完成的合规动作，每项给出依据条文；不同文件要求冲突处单独列出。”

选择理由：事实性强、来源可核验、与产品自身领域相关、无需隐私审批。垂直只是配置，换成医疗/制造/金融只需换语料与提示词。

## 5. 架构

### 5.1 运行拓扑

```text
Browser (React SPA)
   │  HTTPS, REST + SSE, 签名会话
   ▼
Caddy（TLS、反向代理、基础限流）
   ▼
API (FastAPI)
   ├─ Auth：预发账号/访问码 → 签名 cookie；会话隔离
   ├─ RunService（编排、门禁、持久化、run 队列与配额）
   │      │  启动/观察（每个 run 一个子进程，全局并发上限）
   │      ▼
   │  Run Supervisor（独立子进程）
   │      │  in-process
   │      ▼
   │  agent-core Runner → TeamAgent（Leader + Research + Engineering）
   ▼
SQLite + 文件产物 + 快照/事件
```

部署形态：一个 Docker Compose（api + caddy），单机；`runs/` 与 SQLite 挂卷。公网只暴露 443；SSH 仅管理员。评委会话按 cookie 隔离 run 列表与产物路径。

- **每次运行一个子进程**：上游回合结束方式不可靠；进程边界就是运行边界。Supervisor 在流内定时把状态/结果原子写入磁盘，父进程（API）读取并投影为事件。
- **API 不直接承载 Runner**：避免一次运行拖垮整个服务，也让崩溃可隔离、可重放。
- **SQLite + 文件**：run/execution/result/事件沿用现有 `app/repository.py`；产物按 `runs/<run_id>/tasks/<task_id>/<execution_id>/` 落盘。

### 5.2 复用与新增

直接复用（已实现、有断言）：`config_adapter`、`plan`、`execution`、`dependency`、`completion`、`repository`、`knowledge`、`fusion`、`context`、`citations`、`aggregator`、`events`、`budget`、`rework`、`runtime_adapter`。

新增：

| 模块 | 职责 |
|---|---|
| `app/run_service.py` | 编排一次 run：建 workspace/run、编译 spec、启动 supervisor、消费快照、写事件、提交最终结果 |

| `app/retrieval_agent.py` | 检索工具与 Agentic 多轮：子问题、每轮证据、去重、预算裁剪，并记录 `retained/dropped` evidence id |
| `app/conflicts.py` | 跨来源冲突候选检测与报告 |

### 5.3 一次 run 的顺序

1. 创建 run，登记预算/截止；打开该 workspace 授权的语料索引。
2. Supervisor 编译 spec 并构建 team。
3. **Leader 产出结构化计划，应用侧校验后建图**（评审后定为基线，方案 A 不作主路径）：用 `create_tiny_agent(...).run(content, schema=...)` 让 Leader 产出 `TaskPlan`（含 `assignee`），`PlanValidator` 校验（无环、依赖、验收、关键任务 reviewer）→ 无效则修一次或使用最小模板。
4. 应用把通过校验的计划映射为原生任务 DAG：`TaskGraphSpec.assignee` 预分配 + `TeamTaskManager.add_graph`。**不依赖 Leader 自主调用 `create_task`**——那样计划校验只能事后拦截工具调用，且原生 `PlannedTask.role` 只接受 `leader`/`teammate`（两个专业成员共用 `agents["teammate"]` 模板），成员区分必须由 `assignee` 承载。
5. 原生 `scheduled` 调度器扫描 `PENDING(assignee)` 并自动拉起成员（`S_22` 不变量 7）。**成员任务启动前**，应用注入的 rail 调用 `DependencyGate`：前置必须存在**当前 execution** 的业务结果与有效产物；仅有原生 `resolved` 不算。不满足则任务不得进入业务执行，原因写回应用账本并上报 Leader。
6. Research 通过检索工具取证；Engineering 只用交付给它的证据成稿。检索工具记录每次调用返回的 evidence id；该任务的"实际收到"定义见 §6.3。
7. 成员通过 `submit_task_result` 提交结构化结果（claims/evidence/artifacts/acceptance）。`CitationValidator` → `CompletionGate` → 写 repository → 调用原生完成。带 reviewer 的任务进入原生 `IN_REVIEW`，投票结算后再由应用标记业务完成。
8. 失败任务按 `rework` 规则最多一次定向返工（开新 execution）。
9. `Aggregator` 汇总：complete/partial/failed/cancelled，附 limitations。
10. 报告落盘 + 事件投影；流以原生 `team.completed` 标记结束（`team.idle` 只是暂时安静，不作为 run 终点），Supervisor 落最终快照。

## 6. RAG 设计（差异化主线）

### 6.1 导入链

解析 → 结构识别（页码/标题层级/幻灯片）→ 结构感知切片（目标 400–800 字，保留标题上下文，80 字重叠）→ 内容 hash → locator（`page:3` / `section:2.1` / `chars:start-end`）→ FTS5 trigram 索引 →（可选）真实 embedding → 状态 ready / `keyword_only` / failed。

要求：解析或 embedding 失败必须显式记录，不得把失败索引伪装成完成；同一文档的新版本先删旧 chunk。

### 6.2 查询链

授权决定打开哪个索引（不是查询参数过滤）→ Agentic 多轮检索（Leader/Research 拆子问题，每轮独立检索）→ 关键词 + 向量双路 → 按 `chunk_id+revision` 去重 → RRF（`sum(1/(60+rank))`）→ 取上下文窗口内的证据 → 生成带完整 provenance 的 Evidence。

### 6.3 引用与冲突

- 每条 claim 标 `fact`/`inference`/`assumption`；`fact` 必须引用**该任务实际收到的证据**（被预算裁掉的证据不算支撑）。
- **“实际收到”的定义**：该任务 execution 的检索工具调用所返回、并经预算裁剪后保留给模型的 evidence id 集合。检索工具负责裁剪并记录 `retained_evidence_ids` 与 `dropped_evidence_ids`；`ContextBuilder` 组装的任务上下文与这份记录必须一致，引用校验以它为准。这样既保留 Agentic 检索（成员自己发查询），又让“收到”是可判定的，而不是猜模型看没看见。
- 未通过校验的事实改标 `[unverified]` 并排除出其 evidence_refs。
- 同一 claim 在不同来源出现矛盾时，报告并列展示，不消解；无法判定的进入 limitations。
- **冲突检测的 MVP 边界**：只对规范化实体/指标相同、来源不同、取值或要求不一致的 claim 生成**候选冲突**；模型只给判定建议，报告呈现双方原文与出处，不自动裁决。演示使用语料中真实存在的冲突对，不临时编造。
- 检索降级（无 embedding/超时）标记 `keyword_only`，绝不伪造向量分数。

### 6.4 评测

在演示语料上做 20–30 题的小型标注集，脚本化输出：引用准确率、无支撑结论率、Recall@k、跨 scope 泄漏数、平均延迟、总 tokens/calls。指标用于答辩，不用于“模型评分替代验收”。

**通用性验证**：建立第二个最小工作区（约 10 篇另一领域的公开文件），只验证“换语料 + 换提示词即可运行”和“两个 scope 之间不泄漏证据”，不做完整垂直。它同时让“跨 scope 泄漏数”这个指标有实际含义——单一工作区下该指标恒为零，证明不了任何事。

## 7. 里程碑（17 天，单人）

| 日期 | 交付 | 硬门槛 |
|---|---|---|
| D1–D2（10-24~25） | 钉子：应用提交一个 Research → Engineering 的已分配任务图，验证原生调度器拉起成员、成员执行、`submit_task_result` 捕获结构化结果、reviewer 结算、`team.completed` 收尾；同时**抓取真实请求的工具清单**并收敛掉 shell/文件工具；子进程 supervisor + 流内快照 | **成员执行与结构化回传有快照证据**；**请求工具清单不含 shell/文件/spawn**。若原生调度在某一步不成立，退回最小路径：应用直接以成员身份驱动两次单任务执行（仍是真实模型，不伪造） |
| D3–D4 | `RunService` + `TaskBridge` + 门禁接入 + REST/SSE；CLI 端到端 | 一次 run 从目标到 `FinalResult` 落盘 |
| D5 | 登录 + Docker Compose + Caddy + 部署到服务器 | **公网 HTTPS 链接可登录**，能打开工作台壳；这是硬门槛，不达标就当周调整方案 |
| D6–D8 | 前端工作台（目标、任务图、证据抽屉、报告）；预置语料；SSE 实时推进 | 通过公网链接完成一次端到端演示 |
| D9–D11 | 结构感知切片 + Agentic 检索 + 冲突面板 + 评测脚本 + 第二个最小工作区 | 引用可定位到页/节；冲突用例可见；跨 scope 无泄漏 |
| D12–D13 | 演示语料整理、录屏、方案书、README、复现步骤；限流与预算硬化 | 演示视频与材料完成 |
| D14（11-07） | 冻结、回归、提交演练 | 从空环境按文档复现成功；公网链接回归通过 |

## 10. 留给构建者的决定（我的默认，可改）

- 前端：React + Vite + 一个轻量图组件；不用 Next.js（不需要 SSR）。
- 后端：FastAPI + SSE；单进程 API + 每 run 子进程。
- 存储：SQLite（沿用 `repository.py`）+ 文件产物。
- 计划编辑：MVP 不做，只读展示 + 失败重跑。
- 演示垂直：AI 治理与数据合规（可整体替换）。
- 角色：Leader + Research + Engineering 固定三人；不启用动态 spawn。
- 向量检索：凭据可用则接真实 provider；否则明确 `keyword_only`。
- 部署：单台云主机 + Docker Compose（api + caddy），不做多机/K8s；优先使用用户已有资源。
- 登录：预发账号（用户名/密码）或访问码换取签名 cookie；不做注册、找回密码、第三方登录。
- 评委侧不做文件上传；导入与重置只在本机/管理员模式。

## 11. 待用户确认

1. **模型凭据**：用户已确认“现在就提供”，但 `.env.local` 尚未出现。请写入 `MODEL_BASE_URL` / `MODEL_API_KEY` / `MODEL_NAME`（git-ignored）。没有它，D1–D2 钉子无法产出真实证据。embedding 凭据可选，缺失时按 `keyword_only` 演示。

评审形式已明确为“提供可登录链接”，不再作为待确认项。登录采用统一预发账号，但每个浏览器会话只能看到自己会话创建的 run（按 cookie 作用域隔离），因此即使多人共用同一账号，也不会互相看到报告与产物。

## 12. 评审后的决定记录

独立 builder-check 提出了 9 个会改变实现的问题。其中 7 个在此定案，2 个上收给用户（§11）。源码依据同时记录在这一节，便于后续复核。

| # | 问题 | 决定 | 依据 / 影响 |
|---|---|---|---|
| 1 | 控制流基线：Leader 原生建图，还是应用校验后建图 | **应用侧建图**。Leader 用结构化输出产出计划，应用校验、补 `assignee`、调 `add_graph` | 计划校验必须发生在建图之前；原生 `PlannedTask.role` 只有 `leader`/`teammate`，两个专业成员共用 `agents["teammate"]`，成员区分只能靠 `assignee`。原生 `create_task` 不作为主路径 |
| 2 | 结构化结果如何离开原生成员 | 应用注入 `submit_task_result` 工具，校验调用者是任务 assignee 后写 repository，再触发原生完成 | 原生 `member_complete_task` 只接受 `task_id` + `note`，任务行只存指令不存结果；没有这一步，引用校验与完成门禁都无从谈起 |
| 3 | 谁做检索，“实际收到”如何定义 | 成员通过检索工具自己做；工具记录每次返回并裁剪后的 `retained/dropped` evidence id，作为“实际收到”的唯一依据 | 保留 Agentic RAG 卖点，同时让引用校验可判定；避免“模型到底看没看见”这种无法验证的假设 |
| 4 | 凭据时点 | 上收用户（§11.1）；无凭据时先完成离线可验证部分，不伪造回合证据 | D1–D2 钉子的核心证据必须来自真实回合 |
| 5 | 工作区/导入是否用户可见 | 保留**最小可用导入流程**（上传 → 解析 → 索引状态），演示语料预导入但导入路径可现场演示 | 纯预置数据会被视为摆拍；只做最小流程，不做批量管理 |
| 6 | 是否要求跨 run 重跑失败任务 | **明确不做**。run 内有一次定向返工；run 结束后原生 team 已消失，跨 run 重跑需要 checkpoint 恢复或新建 team 对账，属另一功能 | 避免半成品；在文档与 UI 中都不承诺 |
| 7 | 评审看到什么、如何复现 | 用户确认需**可登录链接** → 公网部署、登录、会话隔离是硬要求；同时保留本机复现与只读回放 | 评审形式已确认；部署提前到 D5，成为硬门槛 |
| 8 | 是否需要第二个工作区 | **需要，最小规模**：约 10 篇另一领域公开文件，只验证配置切换与跨 scope 不泄漏 | 单一工作区下“跨 scope 泄漏数”恒为零，无法作为证据 |
| 9 | 冲突检测的标准 | 只生成**候选冲突**：同一规范化实体/指标、不同来源、取值或要求不一致；模型给建议，报告呈现双方原文，不自动裁决 | 自动语义矛盾检测需要独立评测且易误报；演示使用语料中真实冲突对 |
| 10 | 在线评审的访问控制 | 统一预发账号 + 签名会话；每个会话只看自己创建的 run；评委侧禁上传；全局与会话双限流 | 不做用户体系，但公网必须有隔离、限流与成本上限 |
| 11 | 公网工具面 | 关闭 harness 的 shell/文件等能力，只保留团队协作、检索与 `submit_task_result`；上线前抓真实请求的工具清单做断言 | 真实回合观察到 Leader 面前有 29 个工具，其中包含 harness 能力；公网暴露等于把服务器执行权交给输入内容 |

**源码已确认事实（本轮复核）**：

- `scheduled` 调度器会扫描 `PENDING(assignee)` 并自动拉起成员（`S_22` 不变量 7）；`create_task` 的 scheduled 变体带 `assignee`/reviewer 字段。
- 流以 `team.completed` 标记结束并关闭；`team.idle` 是非终态通知，且要求任务板无未终态任务。
- 带 reviewer 的任务在作者完成后进入 `IN_REVIEW`，由 native 投票结算；应用不得另建第二套评审权威。
- 原生 `member_complete_task` 仅接受 `task_id` + `note`；结构化结果必须由应用工具承载。
